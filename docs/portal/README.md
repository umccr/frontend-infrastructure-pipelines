# Portal hosting

`portal.<stage>.umccr.org` serves several independently built and deployed frontends, each on its own
URL path prefix. Source lives in [`lib/portal/`](../../lib/portal/).

- [`onboarding-an-app.md`](./onboarding-an-app.md) — what an app **repository** must do to be hosted
  here. Read this before wiring up a new frontend.
- [`future-improvements.md`](./future-improvements.md) — deferred work and open decisions.

## Apps

| Path          | App       | Repo                 | Bucket                           | Stages            |
| ------------- | --------- | -------------------- | -------------------------------- | ----------------- |
| `/`           | OrcaUI    | `OrcaBus/orca-ui`    | `orcaui-cloudfront-<account>`    | beta, gamma, prod |
| `/v2/`        | OrcaUI v2 | `OrcaBus/orca-ui-v2` | `orcaui-v2-cloudfront-<account>` | beta, gamma, prod |
| `/hub/`       | Hub       | `umccr/hub`          | `hub-cloudfront-<account>`       | beta              |
| `/orcahouse/` | OrcaHouse | `umccr/orcahouse-ui` | `orcahouse-cloudfront-<account>` | beta              |

The registry is [`lib/portal/apps.ts`](../../lib/portal/apps.ts) and is the single source of truth.
A stage with no bucket entry is not provisioned: it gets no bucket, no CloudFront behaviour and no
SPA rewrite entry, and its pipeline skips that deploy stage. That is how an app rolls out beta first.

## How routing works

There is no HTTP redirect. One CloudFront distribution per stage serves every app in place, choosing
an origin by path pattern:

- The root app is the **default behaviour**. Anything not matching another pattern goes there.
- Each path-mounted app gets an **additional behaviour** on `/<prefix>/*` pointing at its own bucket.
- A single **CloudFront Function** on every behaviour rewrites extension-less URLs to the right HTML
  file, so client-side routes and deep links work. How it rewrites depends on the app's
  `clientRouting` mode: an `spa` app gets its single shell, a `static-export` app gets the exported
  HTML for the requested route.

Because the routing table has to be inside the function (CloudFront Functions take no environment
variables), the function's source is generated at synth time from the same app list that creates the
behaviours. See `renderSpaRewriteCode` in
[`infrastructure-stack.ts`](../../lib/portal/infrastructure-stack.ts). This is deliberate: an app
cannot get a behaviour without also getting a routing entry, so the two cannot drift, and a test
asserts the two sets match.

`lambda/spa-rewrite.js` is a **template**. Its `var ROUTE_TABLE = { ... };` line is replaced during
synth and must stay on one line; synth fails with an explicit error if that declaration is missing or
reformatted.

## Request examples

| Request                           | Behaviour | Served                                                                 |
| --------------------------------- | --------- | ---------------------------------------------------------------------- |
| `/`                               | default   | `index.html` from OrcaUI's bucket                                      |
| `/subjects/abc`                   | default   | rewritten to `/index.html`                                             |
| `/runs/wfr.01ABC`                 | default   | rewritten to `/index.html`, the dotted ID is not treated as a filename |
| `/assets/main-abc123.js`          | default   | served by key, not rewritten                                           |
| `/hub/dashboard`                  | `/hub/*`  | rewritten to `/hub/index.html`                                         |
| `/hub/assets/main-abc123.js`      | `/hub/*`  | served by key from Hub's bucket                                        |
| `/hub/...` in a stage without Hub | default   | rewritten to `/index.html`, OrcaUI renders not-found                   |

## Runtime config

Each app gets its own `env.js`, written by the per-stage env config Lambda
(`CodeBuildEnvConfigLambda{Beta,Gamma,Prod}`) after a deploy syncs assets to S3:

| App       | Object                                                 |
| --------- | ------------------------------------------------------ |
| OrcaUI    | `s3://orcaui-cloudfront-<account>/env.js`              |
| OrcaUI v2 | `s3://orcaui-v2-cloudfront-<account>/v2/env.js`        |
| Hub       | `s3://hub-cloudfront-<account>/hub/env.js`             |
| OrcaHouse | `s3://orcahouse-cloudfront-<account>/orcahouse/env.js` |

The targets come from the `PORTAL_APP_TARGETS` environment variable, generated by CDK from the
registry, so adding an app needs no Lambda change. All apps currently receive the same payload.

Invoke it manually with no payload to rewrite every app's `env.js`:

```sh
aws lambda invoke --function-name CodeBuildEnvConfigLambdaBeta response.json
```

Target one app:

```sh
aws lambda invoke --function-name CodeBuildEnvConfigLambdaBeta \
  --cli-binary-format raw-in-base64-out \
  --payload '{"app":"hub"}' response.json
```

Override API versions, as documented in [`docs/orcaui/README.md`](../orcaui/README.md):

```sh
aws lambda invoke --function-name CodeBuildEnvConfigLambdaBeta \
  --cli-binary-format raw-in-base64-out \
  --payload '{"metadata_api_version":"v2"}' response.json
```

Every invocation currently invalidates `/*` on the shared distribution, so one app's deploy evicts
the others' cached objects. Scoping that per app is
[item 4](./future-improvements.md#4-scope-cloudfront-invalidation-per-app).

## App pipelines

Each app has a build-and-deploy pipeline in the toolchain account, built from the shared
[`PortalAppPipeline`](../../lib/portal/app-pipeline.ts) construct. Stages come from the app's
`bucketName`, so a stage with no bucket gets no deploy stage. Prod is always behind a manual
approval.

Each deploy uploads in two passes, so a release cannot break a session that is already open: hashed
assets cache for a year, stable names such as `index.html` never cache. `env.js` is excluded from both
passes because the Lambda owns it and `--delete` would otherwise remove the live config, and `*.map`
is excluded entirely so source maps never become public.

The install phase runs `corepack enable && corepack install`, which resolves each app's own pinned
pnpm from its `packageManager` field rather than duplicating the version here. Node is pinned to 24.

OrcaUI and OrcaUI v2 still have hand-written pipelines predating the construct; migrating them is
[future improvement 6](./future-improvements.md#6-extract-a-reusable-portalapppipeline-construct).

App pipeline stacks are **not** self-mutating. `cdk deploy` updates the pipeline definition without
starting a release:

```sh
pnpm cdk deploy HubAppPipeline OrcaHouseAppPipeline
```

## Deployed names that no longer match

`OrcaUIInfrastructurePipeline`, `OrcaUIInfrastructureStack`, `OrcaUIAssetCloudFrontBucket` and
`CodeBuildEnvConfigLambda*` are shared by every portal app despite the `OrcaUI` prefix. They are
deployed resource identities, and the buckets use fixed physical names with
`RemovalPolicy.DESTROY` and `autoDeleteObjects`, so renaming them deletes live data. New apps get
generated IDs of the form `<Id>AssetCloudFrontBucket`; the two legacy IDs are pinned in
`LEGACY_BUCKET_CONSTRUCT_IDS`.

`test/portal/infrastructure-stack.test.ts` asserts those logical IDs still synthesize, which is the
guard against an accidental rename deleting a bucket.

## Verifying a change

Changes under `lib/portal/**` trigger the shared infrastructure pipeline and redeploy hosting for
every app in all three stages. Confirm the blast radius before merging:

```sh
pnpm test
pnpm cdk synth --quiet -o /tmp/after
# compare against a synth of origin/main; expect additions only for a new app,
# and no removed or renamed logical IDs anywhere
```
